## 1 已經做對、應當保留的決定

這些是本代設計真正的資產，實作時**不要動**：

1. **兩階段 + Phase 1 純計算**（`00` §0.2、§0.3.2）：藍圖是資料、依賴圖可靜態算出。
2. **單一 data-last 曲線**（`00` §0.3.1）：統一所有動詞的成本很低。
3. **「一種掛載、一種提供」**（`00` §0.3.5–6）：拒絕 `mountSync` / `provideSync` 分裂。
4. **公開 token = 字串身分**（`07`）：scatter-usable 是真需求，branded string 是正確答案。
5. **依賴是任意值、不序列化**（`08`）：`function` / `class` / `symbol` 走同一條路徑。
6. **nearest-wins 與 multi 分離**（`04` §4.5）：單值永遠最近者勝。
7. **不做 DOM 投影**（`00` §0.3.10）：邊界正確，代價由配方章補償。
8. **Application 作為隔離邊界**（`11` §11.1）：「不得在 module 全域放 mutable 狀態」是對的。
9. **三條事件通道分離**（`10`）：會話串流 / Context Protocol / 使用者 DOM 事件不混用。
10. **失敗可觀察、不靜默掛起**（`04` §4.3 末、§4.5）。

### 2.1 類型定義：設計期不管

**裁決**：**TypeScript 的型別形狀由實作期決定，不放進設計文件。**

理由：型別是實作的產物；把型別寫進設計文件會讓文件變成「API 提案」，而不是「行為契約」，而且任何型別微調都要回頭改文件——這正是文檔腐化的來源。

因此本代文件的原則是：

- **固定語義與行為**：欄位有什麼意義、什麼時候發生什麼、失敗時看到什麼、順序如何。
- **不固定 TS 語法**：泛型、branding、介面簽章、`pipe` 的推導策略都在實作期決定。
- 需要示意時用**偽代碼或文字描述**，並註明「示意」。
- 規範層（`12`–`14`）一律以「行為條目 + 穩定編號」表達，不以型別表達。

受此裁決影響、原審查列出的項目：型別命名統一（`Token` / `ServiceToken` / `PrivateToken` 三名並存）、`LifecycleEvent` / `DocumentContextError` / `Host` / `Application` / `Blueprint<S>` 的完整定義、`pipe` 的推導策略——**全部轉為實作期決策**，不再寫進文件。

## 5 P1：架構層面的實質建議（已採納）

### 5.1 跨平台生命週期：連線性必須可插拔

**問題**：整個生命週期由「宿主是否連線」驅動，而「連線」是 DOM 概念。非 DOM 平台沒有可插拔的連線訊號來源。

**採納**：`14-ports.md` §14.2 把連線性列為一等埠；DOM adapter 用集中觀察者實作，非 DOM adapter 自訂語意，SSR 報「永遠連線」。

### 5.2 解析傳輸分層

同 Application 走記憶體索引（O(depth)，無 DOM 事件往返），跨 Application 才繞 DOM 事件。nearest-wins 在兩層都成立——跨 Application 由 DOM 冒泡順序天然保證，**同頁多 Application 不需要額外協調**。落點：`14-ports.md` §14.4。

### 5.3 nearest-wins 不要依賴 `stopPropagation()`

第三方在中間節點停止冒泡會讓依賴解析失敗，且對呼叫者不可見。改用 `detail.resolved` 旗標。落點：`10-events.md` §10.1.1、§10.1.4。

### 5.4 pending inject 需要上限

元素目標上的 `injectAll$` 在沒有任何 multi 註冊時永不結案，無上限會無限累積。採納：Application 級上限（預設 1024），超出以 `PENDING_LIMIT_EXCEEDED` 拒絕。落點：`14-ports.md` §14.6、`04-promise-lazy.md` §4.5、`12-errors.md`。

### 5.5 `Application` 需要自己的生命週期

新增冪等的整體釋放；SSR 流程改為 `mount → ready → read → dispose(session) → 釋放 Application`。落點：`14-ports.md` §14.7、`11-composition.md` §11.1、`05-ssr.md` §5。

### 5.6 預設 ports 與便捷入口

使用者不該為了「正常用一次」而自組 adapter：提供內建 adapter 的便捷入口（瀏覽器用、SSR 用各一個），並把「跨 Application 操作同一 Session」從「行為未定義」改成「**必須拒絕**」。落點：`14-ports.md` §14.8、`11-composition.md` §11.4。

### 5.7 Blueprint 合併與模組化組合 —— 🔶 留待實作期

兩個獨立建立的藍圖如何合併尚未定義（feature module 組合的常見需求）。**建議方向**：定義 `pipe` 接受藍圖陣列，或另開合併動詞；合併語意與 `update` 一致（後者整份替換）。本代文件暫不寫死，留待實作期連同 `pipe` 的型別策略一起決定。

### 5.8 `pipe` 的型別策略 —— 🔶 留待實作期

這是全套設計中最容易在實作期爆掉的 TypeScript 問題。可變元組重載、建構子式 API、運算子泛型化三選一。**由實作期決定**（見 §2.1）。

### 5.9 事件協議版本協商 —— 🔶 降級為「最低要求」

兩個 library 副本同頁時需要版本協商。本代改以「互操作的最低要求」（`10-events.md` §10.1.4）描述相容行為，並列出與線上格式的差異表；**不**在本代凍結版本欄位。

### 5.10 單例與暫停表的歸屬統一為 Application

落點：`08-injection.md` §8.1、`02-lifecycle.md` §2.3、`09-mount-host.md` §9.4。
